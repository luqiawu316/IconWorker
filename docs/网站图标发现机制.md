# 纯前端获取网站图标：机制、可行途径与验证

> **约束（本文所有方法必须满足）**：只用 HTML / CSS / JavaScript，在浏览器里直接运行。
> **不采用**：任何自建后端、服务端抓取、浏览器扩展专属 API、构建步骤。
>
> 数据来源：2026-10-10 在 Chrome 126 上，从本地 `file://` 页面发起请求，对 22 个真实站点实测。
> 规范依据：HTML Living Standard（link type "icon"）、W3C Web App Manifest。
> 全文聚焦：**当 `GET /favicon.ico` 返回 404 / 403 / 非图片时，图标还能从哪来、怎么拿、怎么验。**

---

## 0. 速览

`/favicon.ico` 不是标准，只是 IE5 留下的历史约定，浏览器拿它当兜底。现代站点普遍不再依赖它——实测 19 个能取到首页的站点，4 个的 `/favicon.ico` 不可用：

| 站点 | `/favicon.ico` | 图标实际位置 | 纯前端能否拿到 |
| --- | --- | --- | --- |
| example.com | 404 | 无（HTML 声明 `href="data:,"` 主动抑制） | 否（站点确实没有） |
| vuejs.org | 404 | `/logo.svg` | **能**（该站 HTML 跨域可读） |
| rust-lang.org | 404，13 条常见备选路径全部 404 | `/static/images/favicon-32x32.png` 等 | **能**（该站 HTML 跨域可读） |
| npmjs.com | 403（反爬） | 不可得 | 否 |

**三条铁律：**

1. **`HTTP 200` 不等于拿到图标。** 实测 zhihu.com、163.com 对**任意不存在的路径**都返回 `200 text/html`（SPA 兜底）；cloudflare.com 的 `/favicon.ico` 返回 200 但内容是 PNG。必须验真。
2. **能读多少，取决于目标站愿不愿意给 CORS 头。** 这是纯前端方案里最关键的变量，见 §1。
3. **路径猜测永远是概率手段**，HTML 声明与 Manifest 才是权威答案——但前者在纯前端下常常读不到。

### 推荐优先级（纯前端）

| 优先级 | 途径 | 实测可行性 | 说明 |
| --- | --- | --- | --- |
| P0 | 常见路径 + `<img>` 探测（含 `/favicon.ico`） | **可加载 15/19** | 唯一几乎总能执行的手段 |
| P1 | 对探测到的 URL 再走一次 CORS `fetch` 验真 | **可读 5/19** | 能拿到真实状态码 + 魔数，消除误报 |
| P2 | 猜测 manifest 路径并读 `icons[]` | 猜路径命中 3/18 | 质量提升明显（192–512 px） |
| P3 | 读首页 HTML 解析 `<link rel="icon">` | **跨域可读仅 2/20** | 最权威，但多数站点读不到 |
| P4 | 页面其他图像（`logo` / `og:image`） | 同 P3 受限 | 兜底，需标注"非图标" |
| P5 | 存档快照（Wayback 等） | `<img>` 可用 | 站点下线时的人工手段 |
| P6 | 第三方 favicon 服务 | `<img>` 可用 | **隐私与合规风险高，须显式开关** |

## 1. 纯前端的能力边界

这一节决定后面所有结论。同样是"请求一个 URL"，手段不同，能读回来的信息天差地别。

### 1.1 四种手段的能力对照

| 手段 | 能否跨域 | 读到 HTTP 状态码 | 读到响应字节 | 读像素 | 实测 |
| --- | --- | --- | --- | --- | --- |
| `<img>` + `onload`/`onerror` | 是（no-cors） | **否** | 否 | 否 | 可加载 **15/19** |
| `fetch(url, {mode:'cors'})` | 需目标站返回 `ACAO` | **是** | **是** | **是** | 可读 **5/19** |
| `fetch(url, {mode:'no-cors'})` | 是 | 否 | 否（opaque） | 否 | 仅能判可达性 |
| `PerformanceResourceTiming` | — | **实测为 0，不可用** | 否 | 否 | 见 §1.3 |

**核心策略：同一个 URL 先用 `<img>` 探"能不能显示"，如果目标站恰好返回 `ACAO`，再补一次 CORS `fetch` 拿到状态码和字节做验真。** 两档能力递进，不要只做一档。

### 1.2 为什么 `<img>` 能跨域而 `fetch` 不能

`<img>` 属于"可以嵌入的跨域资源"，浏览器允许加载与渲染，但会把它标记为"被污染的"，**禁止脚本读取像素**（canvas 抛 `SecurityError`）。

`fetch` 读内容则必须经过 CORS 检查：目标站必须在响应里带 `Access-Control-Allow-Origin` 且匹配当前页面来源。本地 `file://` 页面的来源是 `null`，很多站点会因此拒绝。

**实测：`/favicon.ico` 的 CORS 可读率 5/19。** 可读的站点多为静态托管平台（实测 react.dev、vercel.com、tailwindcss.com、nextjs.org、rust-lang.org），这类平台通常给静态资源统一加 `ACAO: *`。

### 1.3 已证伪：`PerformanceResourceTiming.responseStatus` 读不到跨域状态码

一个很自然的想法是：用 `<img>` 加载资源，再从 `performance.getEntriesByName(url)` 里读 `responseStatus` 拿状态码。**实测不可行**：

| 目标 | `responseStatus` | `transferSize` | `encodedBodySize` |
| --- | --- | --- | --- |
| `github.com/favicon.ico`（无 TAO） | 0 | 0 | 0 |
| `zhihu.com/favicon.ico`（**返回 `Timing-Allow-Origin: *`**） | **0** | 0 | 0 |
| 不存在的路径 | 0 | 0 | 0 |

字段存在但被清零。**即使目标站返回了 `Timing-Allow-Origin`，实测仍读到 0。** 结论：纯前端无法用性能条目获取跨域资源的 HTTP 状态码，**不要在这上面花时间**。

### 1.4 其他边界

| 想法 | 结论 |
| --- | --- |
| Service Worker 拦截图标请求 | 不能——SW 只能拦截同源请求，对目标站无效 |
| 用 `<iframe>` 加载目标站再读 DOM | 不能——跨域 iframe 的 DOM 不可访问 |
| 用 `<link rel="preload" as="image">` 拿状态 | 不能——只有成功/失败两态，与 `<img>` 等同 |
| canvas 读像素判断空白图 | **仅当目标站返回 `ACAO` 时可行**，见 §4.3 |
| `document.styleSheets` 读 CSS 里的图标 | 不能——跨域样式表内容不可读 |

### 1.5 一个必须记住的反直觉现象

**同一站点的不同路径，CORS 策略可以完全不同。** 实测：

| 站点 | `/favicon.ico` | `/manifest.json` |
| --- | --- | --- |
| nodejs.org | 被拦 | **HTTP 200 可读** |
| tailwindcss.com | **HTTP 200 可读** | 被拦 |
| github.com | 被拦 | 被拦 |
| developer.mozilla.org | 被拦 | 被拦 |

所以**不能因为某一条路径读不到，就放弃该站点的其他路径**。

> 附带提醒：用服务端工具（curl / Node）肉眼看到的 `ACAO` 头，与浏览器实际判定**可能不一致**（实测 nodejs.org 在服务端可见 `ACAO: *`，浏览器却报 "No 'Access-Control-Allow-Origin' header is present"，具体原因未确定，可能与 `Origin: null` 的处理有关）。**一切以浏览器实测为准。**

## 2. 声明与发现机制

站点声明图标的地方有三套并行体系，浏览器会合并考虑，一个都没有时才回落到 `/favicon.ico`。

| 体系 | 位置 | 标准性 | 纯前端可读性 |
| --- | --- | --- | --- |
| HTML link 声明 | `<head>` 内 `<link rel="...icon...">` | `icon` 为标准，其余为厂商扩展 | 差（2/20） |
| Web App Manifest | `icons[]`，由 `<link rel="manifest">` 指向 | W3C 规范（草案阶段） | 中（3/5 已知路径，3/18 猜路径） |
| 约定俗成路径 | 站点根目录固定文件名 | **无标准** | 好（15/19） |

浏览器的选择顺序：

```
解析 HTML → 收集所有 rel 含 "icon" 的 link → 合并 <link rel="manifest"> 的 icons[]
         → 按所需尺寸择优
         → 一个都没有时，才回落到 GET /favicon.ico
```

多候选时的选择规则：

- `sizes` 与目标尺寸精确匹配者优先；
- `sizes="any"`（矢量，如 SVG）视为可缩放到任意尺寸；
- 未声明 `sizes` 的候选由实现自行决定，各浏览器不一致；
- Safari 对 `apple-touch-icon` 有额外偏好，**优先于** Manifest 图标。

## 3. 逐途径详解

### 3.1 HTML 头部 link 标签

实测原文（rust-lang.org，该站 `/favicon.ico` 返回 404）：

```html
<link rel="apple-touch-icon" sizes="180x180" href="/static/images/apple-touch-icon.png?v=ngJW8jGAmR">
<link rel="icon" sizes="16x16" type="image/png" href="/static/images/favicon-16x16.png">
<link rel="icon" sizes="32x32" type="image/png" href="/static/images/favicon-32x32.png">
<link rel="icon" type="image/svg+xml" href="/static/images/favicon.svg">
<link rel="manifest" href="/static/images/site.webmanifest?v=ngJW8jGAmR">
<link rel="mask-icon" href="/static/images/safari-pinned-tab.svg?v=ngJW8jGAmR" color="#000000">
```

#### 属性速查

| 属性 | 取值 | 说明 | 注意 |
| --- | --- | --- | --- |
| `rel` | `icon` | **标准值** | 首选 |
| | `shortcut icon` | 遗留写法，`shortcut` 非规范关键字；浏览器忽略不认识的词，等效 `icon` | 实测 baidu / bilibili / gitee / zhihu 仍在用 |
| | `apple-touch-icon`<br>`apple-touch-icon-precomposed` | 非标准，WebKit 约定，iOS 主屏 | 常为 180×180，质量好；Safari 中优先于 Manifest |
| | `mask-icon` | 非标准，Safari 固定标签页，**单色 SVG** | 必须配 `color`，否则可能不生效；**不可当彩色图标用** |
| | `fluid-icon` | 非标准，GitHub 专有 | 实测仅 github.com，可忽略 |
| | `alternate icon` | 备用图标 | 实测 github 使用 |
| `href` | URL / 相对路径 / `data:` | 相对路径按**文档 URL** 解析，**不是站点根** | 见下方陷阱 1 |
| `sizes` | `16x16`、空格分隔多值、`any` | `any` 用于矢量；缺失时选择行为不确定 | 实测 baidu 用 `sizes="any"` 指向 `.ico` |
| `type` | MIME | 仅提示，**不可信** | 大量站点省略或写错 |
| `media` | 媒体查询 | 按条件选用 | 极少见 |
| `color` | 颜色值 | 仅 `mask-icon` | 缺失则无效 |

另有两个易漏的 meta：

| 标签 | 用途 |
| --- | --- |
| `<meta name="msapplication-TileImage" content="...">` | Windows 磁贴图，常为 144×144 PNG |
| `<link rel="image_src" href="...">` | 遗留的代表图声明，可作低优先级兜底 |

#### 四栏评估

| 项 | 内容 |
| --- | --- |
| **适用条件** | 目标站首页允许跨域读取（实测 2/20）。**实测可读的站点：rust-lang.org、react.dev** |
| **优点** | 最权威，与站点实际生效的图标一致；一次拿到多尺寸多用途的完整候选集；`data:` 内联图标也能取到 |
| **缺点** | 绝大多数站点被 CORS 硬拦；HTML 体量大需限制读取长度；**属性可能不加引号**；相对路径基准是文档 URL |
| **实现思路** | `fetch(首页, {mode:'cors', credentials:'omit', redirect:'follow'})` → 取 `res.text()` → `DOMParser` 解析 → `querySelectorAll('link[rel]')` → 保留 `rel` 含 `icon` 的 → `new URL(href, res.url)` 解析 → 去重 → 逐个验真；失败就跳过，**当作正常情况而非错误** |
| **验证方式** | 断言 HTML 中存在 `rel~="icon"`（同时覆盖带引号、不带引号、`shortcut icon`）；断言解析出的绝对 URL 协议为 http/https 或 `data:`；断言每个 href 能加载 |

#### 三个具体陷阱

**陷阱 1：相对路径的解析基准是文档 URL，不是站点根。**
页面 `https://a.com/blog/post/` 里 `href="icon.png"` → `https://a.com/blog/post/icon.png`；`href="/icon.png"` → `https://a.com/icon.png`。写死站点根会全错。若有 `<base href>`，还需以它为基准。

**陷阱 2：`data:` URI 是"主动抑制"，不是"有图标"。**
实测 example.com 原文（注意属性没有引号）：

```html
<link rel=icon href=data:,>
```

这是刻意声明空图标，用来阻止浏览器自动请求 `/favicon.ico`。解析到 `href` 以 `data:` 开头且**负载为空**时，应判定为"该站点明确不提供图标"，而不是当候选去探测。

**陷阱 3：`DOMParser` 不会执行脚本，但会解析整个文档。**
只需 `<head>` 里的 link，可以对响应文本做长度截断（例如前 512 KB）以省内存——但截断必须在 `<head>` 之后，且要注意部分站点把 link 写在很后面。

#### 可执行检查步骤（人工，不依赖工具）

1. 打开目标页 → 右键「查看网页源代码」（**不是** F12 的 Elements 面板，后者显示的是 JS 注入后的结果）。
2. 搜索 `rel="icon"`、`rel=icon`、`rel="shortcut icon"`、`apple-touch-icon`、`rel="manifest"`、`mask-icon`——**同时搜带引号和不带引号的写法**。
3. 对每个 `href`：绝对 URL 直接用；以 `/` 开头拼站点根；否则以**当前页面的目录**为基准。
4. 逐个访问，确认返回 200 且浏览器显示为图片。

### 3.2 Web App Manifest 的 `icons` 字段

实测原文（rust-lang.org，manifest 本身也在非标准路径）：

```html
<link rel="manifest" href="/static/images/site.webmanifest?v=ngJW8jGAmR">
```

```json
{
  "icons": [
    { "src": "/static/images/android-chrome-192x192.png?v=ngJW8jGAmR", "sizes": "192x192", "type": "image/png" },
    { "src": "/static/images/android-chrome-512x512.png?v=ngJW8jGAmR", "sizes": "512x512", "type": "image/png" }
  ]
}
```

#### 字段速查

| 字段 | 必填 | 说明 |
| --- | --- | --- |
| `src` | **是** | 相对路径按 **manifest 文件自身 URL** 解析，不是站点根 |
| `sizes` | 建议 | `192x192`、空格分隔多值、或 `any`（矢量） |
| `type` | 可选 | MIME 提示；省略会迫使浏览器做 MIME 嗅探 |
| `purpose` | 可选 | `any`（默认）/ `maskable`（可被系统裁形，安全区为内侧 80%）/ `monochrome`（单色蒙版） |

#### 四栏评估

| 项 | 内容 |
| --- | --- |
| **适用条件** | 能定位到 manifest URL 且能读取它。**规范规定 manifest 以 CORS 方式请求**，CDN 托管 manifest 时必须下发 `ACAO`，所以它的跨域可读率显著高于 HTML |
| **优点** | 结构化 JSON，解析零成本；图标尺寸大（192–512 px），质量远优于 16×16 的 ico；一次得到多尺寸多用途集合 |
| **缺点** | 不是所有站点都有；路径不规范（实测 rust-lang.org 在 `/static/images/`、tailwindcss.com 在 `/favicons/` 且带 query 串）；**猜路径命中率只有 3/18**；JSON 可能不合法；`icons` 可能为空或指向 404 |
| **实现思路** | ① 若 HTML 可读，取 `<link rel="manifest">`；② 否则猜路径：`/manifest.json`、`/site.webmanifest`、`/manifest.webmanifest`；③ CORS fetch + 校验；④ 用 `new URL(icon.src, manifestURL)` 解析每个图标 |
| **验证方式** | 断言 HTTP `200`；断言能 `JSON.parse` 且结果是对象；断言 `Array.isArray(json.icons)`；断言 `icons` 非空；对每个 `src` 断言可加载 |

#### 实测：猜路径命中 3/18

| 站点 | 结果 |
| --- | --- |
| nodejs.org | 命中 `/manifest.json`（2 个图标） |
| react.dev | 命中 `/site.webmanifest`（2 个图标） |
| vercel.com | 命中 `/manifest.webmanifest`（2 个图标） |
| rust-lang.org / nextjs.org | 三个路径均 `404`（但 **HTTP 可读**，说明该站 ACAO 生效，只是路径猜不中） |
| 其余 13 个 | 均被 CORS 拦（`TypeError`） |

**关键细节：`TypeError` 是二义的**——既可能是"文件不存在"，也可能是"存在但没有 `ACAO`"。所以 CORS 失败**不能**推出"没有 manifest"。反之，能收到 `404` 反而说明该站 CORS 是通的。

**收益评估（诚实结论）**：在实测的 18 个站点里，manifest 猜路径**没有发现任何"路径探测拿不到、只有 manifest 能拿到"的站点**——nodejs.org / vercel.com 的 `/favicon.ico` 本身都可用。它的真实价值是**质量提升**（拿到 192–512 px），而非"唯一途径"。

#### 可执行检查步骤（人工）

1. 源码里搜 `rel="manifest"`；找到 `href` 就访问。
2. 找不到就手工试 `/manifest.json`、`/site.webmanifest`、`/manifest.webmanifest`。
3. 打开返回值，**确认是 JSON 而不是 HTML**（直接打开会显示 `{...}`；若显示网页则失败）。
4. 从 `icons[].src` 取路径，相对路径按 manifest 自身地址拼绝对 URL，逐个访问。

### 3.3 常见替代路径

**这是纯前端的主力手段**——实测 `<img>` 可加载率 15/19。

| 路径 | 说明 | 实测命中 |
| --- | --- | --- |
| `/favicon.ico` | 历史兜底，必试 | github、MDN、cloudflare、vercel、nodejs、baidu、bilibili、zhihu、163、gitee、juejin、python、react.dev、nextjs、tailwindcss（15 个） |
| `/favicon.png` | 现代替代 | nodejs.org |
| `/favicon.svg` | 矢量，`sizes="any"` | MDN |
| `/favicon-32x32.png` `/favicon-16x16.png` | realfavicongenerator 等工具默认产物 | MDN、react.dev |
| `/apple-touch-icon.png` | iOS 约定，常见 180×180 | github、nodejs、MDN、react.dev |
| `/apple-touch-icon-precomposed.png` | iOS 旧版 | nodejs |
| `/apple-touch-icon-180x180.png` | 尺寸显式命名 | github |
| `/apple-touch-icon-{57,60,72,76,114,120,144,152,180,256}x…png` | 尺寸矩阵 | vercel.com |
| `/android-chrome-192x192.png` `/android-chrome-512x512.png` | Manifest 图标落地路径 | — |
| `/mstile-150x150.png` | Windows 磁贴 | — |
| `/assets/favicon.ico` `/static/favicon.ico` `/img/favicon.ico` `/images/favicon.ico` | 构建产物常见目录 | gitee(`/assets/`)、python(`/static/`)、zhihu(`/static/`)、nodejs(`/static/`) |
| `/browserconfig.xml` | Windows 磁贴配置文件，内含 `<square150x150logo src="...">` | **react.dev**（实测唯一真命中；vercel/zhihu 返回的是 SPA 兜底 HTML，须校验是 XML） |
| `/manifest.json` `/site.webmanifest` `/manifest.webmanifest` | 见 §3.2 | 见 §3.2 |

#### 四栏评估

| 项 | 内容 |
| --- | --- |
| **适用条件** | 无。不需要读 HTML，不需要 CORS 权限 |
| **优点** | 实现最简单；不受 CORS 影响（`<img>` 即可）；是 HTML / Manifest 都拿不到时**唯一的兜底** |
| **缺点** | 纯概率，**并非规范要求**；对 rust-lang.org / vuejs.org 这类站点命中率为 0（实测 13 条备选路径全 404）；产生多次无效请求；易受 SPA 兜底路由干扰产生误报 |
| **实现思路** | 有序候选列表逐个探测，每个带独立超时；**用 `<img>` 的 `onload`/`onerror` 判断**；对成功项**再补一次 CORS `fetch` 验真**（若能读到，就能拿真实状态码与字节） |
| **验证方式** | 断言 `img.onload` 触发且 `naturalWidth > 0` 且 `naturalHeight > 0`；能 CORS 读到的，额外断言状态码为 200 且**魔数**为图片格式 |

#### 必须注意的三个陷阱

**陷阱 1：`200` ≠ 是图片。** 实测：

| URL | HTTP | 声称 | 真实内容 |
| --- | --- | --- | --- |
| `cloudflare.com/favicon.ico` | 200 | `image/vnd.microsoft.icon` | **PNG**（908 B） |
| `developer.mozilla.org/favicon.ico` | 200 | `image/x-icon` | **PNG**（763 B） |
| `nodejs.org/favicon.ico` | 200 | `image/png` | PNG（1130 B） |
| `zhihu.com/<任意不存在路径>` | **200** | `text/html` | HTML（SPA 兜底） |
| `example.com/favicon.ico` | 404 | `text/html` | HTML 错误页 |

**扩展名与 `Content-Type` 都不可信。** 纯前端能做的验真分两档：

- **能 CORS 读取时**（实测 5/19）：用 `fetch` 读字节，做魔数嗅探——

| 格式 | 首字节特征 |
| --- | --- |
| PNG | `89 50 4E 47 0D 0A 1A 0A` |
| ICO | `00 00 01 00` |
| GIF | `GIF87a` / `GIF89a` |
| JPEG | `FF D8 FF` |
| WebP | `RIFF` … `WEBP` |
| SVG | 文本以 `<svg` / `<?xml` 开头且含 `<svg` |
| HTML | 文本以 `<!doctype html` / `<html` 开头 |

- **不能 CORS 读取时**（多数情况）：只能靠 `<img>` 的成功/失败二元信号 + `naturalWidth/Height` 是否合理（排除 1×1）。**这时无法区分"404 错误页"与"真的没有"**，必须在 UI 文案上诚实说明。

**陷阱 2：`.ico` 是容器，不是单一尺寸。** 实测解析 ICO 目录：

| 文件 | 内含图像 | 总大小 |
| --- | --- | --- |
| `github.com/favicon.ico` | 16×16、32×32 | 6518 B |
| `zhihu.com/favicon.ico` | 32×32 | 4286 B |
| `baidu.com/favicon.ico` | 64×64 | 16958 B |
| `juejin.cn/favicon.ico` | 48×48、32×32、16×16 | 15086 B |

纯前端通过 `<img>` 加载 `.ico` 时，`naturalWidth` 只反映浏览器选中的那一张。**"图标多大"取决于浏览器选了容器里的哪一张。**

**陷阱 3：SPA catch-all。** 部分站点对任意路径都返回 200 + HTML（实测 zhihu.com、163.com）。**只判断状态码必然误报。**

#### 可执行检查步骤（不依赖工具）

1. 浏览器地址栏依次访问候选路径，看是显示图片、下载文件，还是显示网站页面。
2. 显示图片 → 按 F12 → Network 面板刷新 → 找到该请求，确认 `Status` 与 `Content-Type`。
3. 确认真格式：下载后用十六进制查看器看头 8 字节，对照上表。
4. 若显示的是网站首页或错误页 → 是 catch-all 兜底，判定为**不存在**。

### 3.4 页面中的其他图像资源（`logo` / `og:image` / `twitter:image`）

实测原文：

| 站点 | 标签 | 地址 |
| --- | --- | --- |
| vuejs.org | `og:image` | `https://vuejs.org/images/logo.png` |
| rust-lang.org | `og:image` / `twitter:image` | `.../rust-social-wide.jpg` / `rust-social.jpg` |
| nodejs.org | `twitter:image` | `https://nodejs.org/static/images/logo-hexagon-card.png` |
| gitee.com | `og:image` | `https://gitee.com/static/images/logo.svg` |

#### 四栏评估

| 项 | 内容 |
| --- | --- |
| **适用条件** | HTML 可读取（与 §3.1 相同的 CORS 限制，实测 2/20） |
| **优点** | 有 HTML 就有；尺寸大、清晰度高；品牌一致性一般较好 |
| **缺点（关键）** | **`og:image` / `twitter:image` 是"社交分享卡片图"，不是图标。** 常见为 1200×630 横幅，含标题文字、渐变背景、营销文案，**直接当 favicon 用会严重失真**；logo 常是含文字的组合标，缩到 16 px 后不可辨认 |
| **实现思路** | 仅作**最后兜底**；优先选方形且以 logo 命名的资源（`logo.svg`、`logo.png`）；`og:image` 只在无任何其他候选时使用 |
| **验证方式** | 断言可访问；断言宽高比接近 1:1（否则降级）；人工确认 16×16 下仍可辨认、无大面积文字 |

#### 分级使用建议

| 资源 | 可用性 |
| --- | --- |
| `<img>` 中 `src`/`alt` 含 `logo` 且为方形 | 可作兜底，需标注 |
| `logo.svg` / `apple-touch-icon` 类 | 可作兜底 |
| `og:image`（1200×630 横幅） | **仅最后兜底**，需强提示"非图标" |
| `twitter:image` | 同上 |
| 页面首屏大图、产品截图 | **不应使用** |

**风险标注**：把站点品牌图抓来展示，若仅用于"指明该 URL 对应哪个站点"通常可接受；若用于暗示合作/背书、或用作自身产品的品牌资产，则涉及商标侵权风险。**必须在 UI 上保留来源 URL。**

### 3.5 存档快照（Wayback Machine 等）

| 项 | 内容 |
| --- | --- |
| **可用形式** | `https://web.archive.org/web/<年>id_/<原始图标URL>`，纯 `<img>` 加载即可 |
| **实测** | `<img>` 加载 `https://web.archive.org/web/2024id_/https://github.com/favicon.ico` → **OK 32×32**（CORS `fetch` 被拦，但显示没问题，够用） |
| **适用条件** | 站点曾被存档且快照仍在 |
| **优点** | 站点已下线或改版后仍能取到历史图标；无需目标站配合；**纯前端可实现** |
| **缺点** | **快照可能过期数年**，与站点当前图标不符；快照可能随时被删除；有速率限制；返回的可能是存档服务自己的错误页；**无法 CORS 读取，因此拿不到状态码，只能靠 `<img>` 成败判断** |
| **合规风险** | 第三方服务，需遵守其使用条款与 robots 策略；批量调用可能被限流或封禁；存档内容版权仍属原站 |
| **实现思路** | 仅在正常途径全部失败后作为可选兜底；**必须把"这是历史快照 + 时间戳"标注在 UI 上** |
| **验证方式** | 断言 `<img>` 能加载且尺寸合理；断言展示的快照年份；与源站当前图标对比，不一致时明确提示 |

### 3.6 第三方 favicon 服务

| 服务 | 形式 | 实测纯前端可用性 |
| --- | --- | --- |
| Google S2 | `https://www.google.com/s2/favicons?domain=example.com&sz=128` | `<img>` **OK 128×128**；CORS 被拦 |
| DuckDuckGo | `https://icons.duckduckgo.com/ip3/example.com.ico` | `<img>` **OK 32×32**；CORS 被拦 |
| unavatar.io | `https://unavatar.io/<provider>/<id>` | `<img>` **失败**；CORS HTTP 200（实测不可用） |

| 项 | 内容 |
| --- | --- |
| **适用条件** | 站点图标能被服务方抓取到（服务方自己用的也是 §3.1–3.3 的方法） |
| **优点** | 一个 URL 搞定，代码量最小；**服务方已解决 CORS**，`<img>` 直接可显示；对纯前端最省事 |
| **缺点** | **图标可能与站点当前图标不一致**（服务方缓存过期）；服务可能返回默认占位图而非失败，**无法区分"没抓到"和"抓到了"**；服务可能随时变更或下线（历史上已有 Logo API 停服先例）；**CORS 被拦意味着拿不到状态码，也无法验真** |
| **合规与隐私风险（高）** | ① **把用户查询的域名泄露给第三方**，形成浏览偏好画像；② 需遵守服务方 ToS，多数限制批量抓取，商用需授权；③ 返回图像版权/商标权仍属原站，第三方只是缓存者，**不构成授权**；④ 涉密、内网、合规敏感环境**不可使用** |
| **实现思路** | **做成显式开关，默认关闭**；启用前在界面写明数据会发往第三方；作为最后兜底而非主路径 |
| **验证方式** | 断言 `<img>` 能加载；断言尺寸合理；**对服务方的已知默认占位图做哈希比对以识别"假成功"**；与源站直连结果对比，不一致时提示 |

> 本次全部实测**刻意未使用任何第三方服务**，以保证"只请求目标站点"这一原始约束不被破坏。

## 4. 多候选时如何选择

| 权重 | 维度 | 判断规则 |
| --- | --- | --- |
| 1 | **来源权威性** | HTML 声明 > Manifest > 约定路径 > 页面图像 |
| 2 | **尺寸** | **32–180 px 区间最佳**；16×16 偏小，512×512 对 favicon 用途过大且浪费流量 |
| 3 | **格式** | SVG（可缩放）> PNG > ICO > WebP > JPEG（无透明通道，作图标有白底问题）> GIF |
| 4 | **用途标记** | `purpose="maskable"` 含安全区留白，直接当 favicon 会显得偏小；`purpose="monochrome"` 是单色蒙版，**不能**当彩色图标 |
| 5 | **可访问性** | 排除超时、加载失败、1×1 占位图；同分时优先能 CORS 读取（可验真）的地址 |
| 6 | **代表性** | 排除 `og:image` 横幅、含文字的组合标、纯白/全透明图；优先方形且内容居中 |

综合评分（可直接实现）：

```
score = 来源权重 + 尺寸加成 + 格式加成 - 惩罚
来源权重: HTML声明=200, Manifest=160, 约定路径=90..70, 页面图像=30
尺寸加成: min(50, round(min(宽,高) / 4))        # 180px → +45, 16px → +4
格式加成: SVG=+10, PNG=+5, ICO=0, WebP=-5, JPEG=-10
惩罚:     maskable=-5, monochrome=-100(不可用), 宽高比偏离1:1=-20
```

同分时：**展示全部可用候选**，最高的作主图，其余列为备选——不要把选择权完全交给算法。

## 5. 最终推荐流程（纯前端）

```
输入 raw
  ↓
归一化：补协议、校验域名、得到 origin
  ↓
[1] CORS 读取首页 HTML（大概率失败，失败不算错误，仅记录提示）
      ├─ 成功 → 解析所有 rel 含 "icon" 的 <link>（含 sizes/type），按 sizes 降序入候选池（优先级最高）
      ├─ 记录 <link rel="manifest">、<meta msapplication-TileImage>、og:image / twitter:image（低优先级兜底）
      └─ 遇到 href 为空的 data: URI → 记录"站点主动声明无图标"
  ↓
[2] 猜测 manifest 路径（/manifest.json、/site.webmanifest、/manifest.webmanifest）
      └─ CORS fetch → 校验 JSON 可解析 → 遍历 icons[] → 按 src 相对 manifest URL 解析 → 入候选池
      └─ 注意：CORS 失败 ≠ 不存在，不要据此下结论
  ↓
[3] 逐个探测约定路径（/favicon.ico 必试），每个独立超时
      ├─ 用 <img> 判断能否显示，读 naturalWidth/Height
      └─ 若该 URL 同时能 CORS fetch → 读字节做魔数嗅探，消除 SPA 兜底误报
  ↓
[4] 候选池为空 → 用页面图像兜底，UI 标注"非图标来源"
  ↓
[5] 打分排序 → 主图 + 备选列表
  ↓
[6] 全部失败 → fetch(origin, {mode:'no-cors'}) 探测可达性
      ├─ 可达 → "站点可达，但未找到公开图标"
      └─ 不可达 → "域名无法解析或网络不可达"
  ↓
输出：图标、来源 URL、尺寸、格式、来源类型、是否兜底、是否可验真
```

**必须遵守的实现要点：**

- 每个探测都要**独立超时**（图片 6 s、HTML 8 s、可达性 6 s），超时按失败处理，不能让请求悬空。
- 界面回调一律走**令牌校验**，新查询要能取代旧查询，**不能静默丢弃用户输入**。
- `<img>` 探测时**绝不设 `crossOrigin`**——设了会要求目标站返回 CORS 头，导致大面积失败。
- 但可以**并行做一次带 `crossOrigin='anonymous'` 的尝试**，成功则解锁状态码 + 魔数校验。
- 失败提示必须**区分原因**：无图标 / 可达但无图标 / 域名不可达 / 被反爬拦截。

## 6. 验证清单

### 6.1 传输层

- [ ] 目标 URL 返回 `200`
- [ ] **未把 `200` 直接当成"图标存在"**——已通过魔数嗅探或 `<img>` 成功率交叉确认
- [ ] 确认未被重定向到登录页 / 验证码页 / 站点首页（对比最终 URL 与请求 URL）
- [ ] 记录了 `Content-Type` 与实际格式的差异（`image/x-icon` 可能是 PNG）
- [ ] 异常大（可能是整张海报）或异常小（可能是 1×1）的响应已被识别
- [ ] 每个请求都有超时且有兜底分支，无请求悬挂

### 6.2 声明层

- [ ] HTML 中确认存在 `rel~="icon"`（**同时覆盖带引号、不带引号、`shortcut icon`**）
- [ ] 已收集 `apple-touch-icon`、`mask-icon`（含 `color`）、`msapplication-TileImage`、`image_src`
- [ ] 相对路径按**文档最终 URL** 解析正确（含 `<base href>` 的页面已额外处理）
- [ ] `data:` URI 已区分"真实内联图标"与"`data:,` 空负载抑制声明"
- [ ] Manifest JSON **可解析**（`JSON.parse` 不抛异常且为对象）
- [ ] 断言 `Array.isArray(json.icons)` 且非空
- [ ] Manifest 内的相对 `src` 按 **manifest 自身 URL** 解析，而非站点根
- [ ] `/browserconfig.xml` 返回内容**已确认是 XML 而非 SPA 兜底 HTML**

### 6.3 资源层

- [ ] 每个候选图标可加载（`<img>` `onload` 触发）且格式正确（能 CORS 读取时用魔数校验）
- [ ] 尺寸合理：`naturalWidth` / `naturalHeight` 均 > 0，且不是 1×1 占位图
- [ ] `.ico` 容器的多尺寸特性已考虑（不要按单一尺寸理解）
- [ ] 宽高比接近 1:1；对 `og:image` 类横幅已单独标注
- [ ] `purpose="monochrome"` 的蒙版图未被当彩色图标使用
- [ ] 能 CORS 读取时，已用 canvas 检查是否全透明/纯色占位图

### 6.4 合规层

- [ ] 确认**未向任何自建后端**发送请求
- [ ] 确认除目标站点外**未请求第三方**；若启用第三方服务或存档，已在界面明确告知
- [ ] 未使用浏览器扩展专属 API、未要求任何服务端配合
- [ ] 若启用存档/第三方：已标注数据来源、快照时间与可能不一致的风险
- [ ] 已提示商标/版权归属原站，界面保留来源 URL

### 6.5 降级与提示

- [ ] 空输入 → 明确提示
- [ ] 格式错误（无后缀 / 含空格 / 非 http 协议 / 缺主机名）→ 各自独立提示
- [ ] 站点可达但无图标 → 提示"可达但未找到"，并列出尝试过的路径
- [ ] 域名不可达 → 与上一条**区分开**（用 `no-cors` 探测区分）
- [ ] 被反爬拦截（403 / 429）→ 单独提示，不与"无图标"混淆
- [ ] **CORS 被拦时，提示语不得暗示"该站没有图标"**，只能说明"无法读取声明"
- [ ] 全程无未捕获异常，页面不崩溃

### 6.6 交叉验证（判断结果是否可信）

- [ ] 把取到的图标 URL 直接在浏览器打开，确认显示的是目标站点的图标而非占位图或错误页
- [ ] 与浏览器地址栏实际显示的图标目视比对
- [ ] 换一个网络环境复测，确认不是本地缓存 / CDN 特例
- [ ] 若结果来自第三方服务或存档，与源站直连结果比对，不一致时以源站为准

## 7. 不符合约束、不采用的方法

明确排除，以免后续误用。

| 方法 | 为何不符合 |
| --- | --- |
| 服务端抓取首页 HTML | 需要后端 |
| 任意 CORS 代理（`corsproxy` 之类） | 需要第三方服务中转，本质是后端 |
| 浏览器扩展 API（`chrome://favicon`、`favicon` 权限） | 需要扩展，不是纯网页 |
| 读取浏览器磁盘缓存 / `chrome://cache` | 网页 JS 无权限 |
| Service Worker 拦截目标站请求 | SW 仅能拦截同源请求 |
| 抓取搜索引擎结果页 | 跨域不可行 + 违反 ToS |
| 构建步骤 / 打包工具 | 违反"直接打开即可运行" |
| `PerformanceResourceTiming` 读跨域状态码 | **实测为 0，不可用**（见 §1.3） |

**已被本次实测判定为不可用的具体手段：**

| 手段 | 实测结果 |
| --- | --- |
| `PerformanceResourceTiming.responseStatus` 读跨域状态码 | 恒为 0（含返回 `Timing-Allow-Origin: *` 的站点） |
| 无 `ACAO` 时用 canvas 读像素 | 加载即失败（`crossOrigin='anonymous'` 要求 CORS） |
| unavatar.io 作为图标源 | `<img>` 加载失败 |

| npmjs.com | 403 | `text/html` 5799 B | 反爬拦截 |

### A.3 格式与声明不符

| URL | HTTP | 声称 | 实际 |
| --- | --- | --- | --- |
| `cloudflare.com/favicon.ico` | 200 | `image/vnd.microsoft.icon` | PNG 908 B |
| `developer.mozilla.org/favicon.ico` | 200 | `image/x-icon` | PNG 763 B |
| `nodejs.org/favicon.ico` | 200 | `image/png` | PNG 1130 B |
| `zhihu.com/<任意路径>` | 200 | `text/html` | HTML（SPA 兜底） |

### A.4 图标托管在第三方 CDN 的站点

| 站点 | 图标主机 |
| --- | --- |
| bilibili.com | `i0.hdslb.com` |
| zhihu.com | `static.zhihu.com` |
| juejin.cn | `lf-web-assets.juejin.cn` |
| vercel.com | `assets.vercel.com`、`*.public.blob.vercel-storage.com` |
| baidu.com | `psstatic.cdn.bcebos.com` |
| github.com | `github.githubassets.com` |

**站点图标与站点本身常常不同源**，任何"限定同域"的假设都会漏掉命中。纯前端下这一点尤其重要：**跨域加载 `<img>` 完全没有问题，限制只作用于 `fetch` 读取内容。**

## 附录 B：方法可靠性汇总

| 方法 | 是否标准 | 纯前端可行 | 结果权威性 | 需要 CORS | 合规风险 | 建议定位 |
| --- | --- | --- | --- | --- | --- | --- |
| HTML `rel="icon"` | 是 | 有限（2/20） | 最高 | 是 | 无 | 首选（能读则读） |
| `rel="shortcut icon"` | 遗留 | 有限 | 高 | 是 | 无 | 与上等同处理 |
| `rel="apple-touch-icon"` | 非标准 | 有限 | 高 | 是 | 无 | 高质量备选（常 180 px） |
| `rel="mask-icon"` | 非标准 | 有限 | 中 | 是 | 无 | 单色场景，不可当彩色图标 |
| Manifest `icons[]` | 是（草案） | **可** | 高 | 是 | 无 | 质量提升的首选 |
| 常见路径 + `<img>` | **否** | **可（15/19）** | 中 | **否** | 无 | 主力手段 |
| CORS 复核探测结果 | — | **可（5/19）** | 高 | 是 | 无 | 消除误报的关键补充 |
| `/browserconfig.xml` | 非标准 | 可 | 中 | 是 | 无 | 低优先级补充 |
| `og:image` / `twitter:image` | 否（非图标） | 有限 | 低 | 是 | 低（需标注） | 最后兜底 |
| 存档快照 | — | **可（`<img>`）** | 低（可能过期） | 否 | 中 | 站点下线时的人工手段 |
| 第三方 favicon 服务 | — | **可（`<img>`）** | 中（不可控） | 否 | **高** | 显式开关，须告知 |
| 浏览器缓存 / 扩展 API | — | **否** | — | — | 无 | 排除（需扩展） |
| 搜索引擎结果 | — | **否** | 低 | — | **高** | 排除（不可行 + 违反 ToS） |
| 性能条目读状态码 | — | **否** | — | — | 无 | 排除（实测为 0） |
